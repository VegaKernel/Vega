# Перенос сервера на Vega

Остановите исходный TShock, основной сервер Vega и все sandbox-процессы, сохраните полную резервную копию и сначала проверьте перенос на копии развёртывания. Команды запускаются из папки Vega, выполняют офлайн-перенос и завершают процесс без запуска Terraria. Исходная база TShock открывается только для чтения.

## Старое хранилище SSC Vega

```powershell
.\Vega.Server.exe --vega-migrate-primary-ssc
```

Переносит `data/primary-characters.json` в общий `data/sandboxes/ssc.json`, сохраняя прочие миры. Конфликтующие персонажи не перезаписываются. Старый файл архивируется как `primary-characters.json.migrated`; существующее общее хранилище сохраняется в отдельную резервную копию. Только после успешного переноса включайте `enabled: true` и `authoritative: true` в `config/primary-character-persistence.json`.

## Перенос текущей схемы SQLite или MySQL TShock

Сначала создайте и проверьте группы Vega и их разрешения. В `groups.json` задайте явное сопоставление групп TShock с существующими группами Vega. Например, если `member` соответствует обычной группе `default`:

```json
{"member":"default"}
```

Затем выполните необходимые команды для копии базы TShock:

```powershell
.\Vega.Server.exe --vega-import-tshock-accounts "D:\TShock\tshock.sqlite" "D:\Migration\groups.json"
.\Vega.Server.exe --vega-import-tshock-ssc "D:\TShock\tshock.sqlite" classic
.\Vega.Server.exe --vega-import-tshock-bans "D:\TShock\tshock.sqlite"
.\Vega.Server.exe --vega-import-tshock-whitelist "D:\TShock\whitelist.txt" on
.\Vega.Server.exe --vega-import-tshock-regions "D:\TShock\tshock.sqlite" 12345678 "D:\Migration\groups.json"
.\Vega.Server.exe --vega-import-tshock-warps "D:\TShock\tshock.sqlite" 12345678 "00000000-0000-0000-0000-000000000001"
```

Замените пример числового `WorldID` и GUID на реальные идентификаторы соответствующего `.wld`. Для Journey-мира укажите `journey` вместо `classic`.

### Если исходный TShock использует MySQL

Вместо пути к SQLite указывайте `'@mysql'` (в кавычках для PowerShell).
Строку подключения передайте через `VEGA_TSHOCK_MYSQL_CONNECTION` — не в
аргументах командной строки и не в Git. Например, загрузите её из локального
файла с ограниченными правами доступа:

```powershell
$env:VEGA_TSHOCK_MYSQL_CONNECTION = (Get-Content -LiteralPath 'D:\Migration\tshock-mysql.connection' -Raw).Trim()
.\Vega.Server.exe --vega-import-tshock-accounts '@mysql' 'D:\Migration\groups.json'
.\Vega.Server.exe --vega-import-tshock-ssc '@mysql' classic
.\Vega.Server.exe --vega-import-tshock-bans '@mysql'
.\Vega.Server.exe --vega-import-tshock-regions '@mysql' 12345678 'D:\Migration\groups.json'
.\Vega.Server.exe --vega-import-tshock-warps '@mysql' 12345678 '00000000-0000-0000-0000-000000000001'
```

Используйте исходного пользователя с правом `SELECT` и явным именем базы.
Каждый конвертер MySQL читает согласованный снимок в транзакции только для
чтения. Остановите запись в TShock на всё время переноса: команды независимы.
Вайтлист по-прежнему импортируется из текстового файла.

### Выбор базы назначения Vega

Настройте существующий `config/database.json`: `provider` может быть `sqlite`,
`mysql` или `postgresql`. Для MySQL создайте **отдельную** целевую базу и
передайте её строку подключения через `VEGA_DATABASE_CONNECTION_STRING`
(либо переменную, указанную в `connectionStringEnvironmentVariable`).
Имена MySQL-баз TShock и Vega должны отличаться, в том числе на разных
хостах: это защита от случайной записи в исходную схему. SQLite-файлы
источника и назначения также должны быть разными.

Аккаунты, баны и регионы импортируются транзакционно в выбранную СУБД.
Для внешней базы перед импортом строк создаётся логический дамп в
`data/migration-backups/<уникальный-каталог>/`; установите `mysqldump` или
`pg_dump` и предоставьте права резервного копирования. Дамп создаётся после
инициализации схемы, поэтому обязательно сохраните полную копию базы и
развёртывания ещё до её обновления. SSC, варпы и вайтлист используют штатные
файловые хранилища Vega независимо от СУБД.

- Аккаунты: сохраняет исходные ID, имена, явно сопоставленную группу и дату последней активности. Импорт выполняется в пустую таблицу аккаунтов. Поддерживаемый BCrypt-хеш обновляется до штатного PBKDF2 Vega после успешного входа. Хеши в консоль не выводятся. Неподдерживаемые хеши, work factor вне диапазона 4–14 и пароли BCrypt длиннее 72 байт UTF-8 требуют предварительного сброса в TShock.
- SSC: переносит текущую раскладку из 350 слотов, инвентарь, банки, экипировку, loadout, характеристики, внешний вид и постоянные флаги. Проверяет связь персонажа с импортированным аккаунтом. Старые неоднозначные раскладки не угадываются и не дополняются автоматически. Конфликтующее существующее состояние сохраняется без замены.
- Баны: переносит действующие IP, UUID, имена и аккаунты. Повторный импорт не создаёт дубликаты и не восстанавливает отозванные Vega баны; хранилище используется всеми мирами.
- Вайтлист: переносит IP и CIDR из текстового файла в пустой отключённый общий whitelist. Параметр `on` или `off` задаёт требуемое состояние. Неверная запись отклоняет весь импорт; исходный файл не меняется.
- Регионы: переносит выбранный мир, размеры, владельцев, приоритет, защищённость, разрешённые аккаунты и явно сопоставленные группы. Целевой набор регионов основного мира должен быть пустым.
- Варпы: переносит выбранный мир и сохраняет скрытые точки; создаёт новый файл, не перезаписывает существующий. Координаты переводятся из тайлов TShock в пиксели Vega для стандартной геометрии игрока.

Группы и разрешения не переводятся автоматически по совпадению имени: семантика прав TShock и Vega различается. Поддержаны текущие схемы SQLite/MySQL TShock и назначения SQLite/MySQL/PostgreSQL. Старые схемы, данные сторонних плагинов и реальный клиентский цикл SSC требуют отдельной квалификации. Подробности резервного копирования и отката — в [полной инструкции](../migration.md).
