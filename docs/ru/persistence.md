# Хранение данных

Vega предоставляет единый доменно-ориентированный слой хранения с тремя реляционными провайдерами: SQLite, PostgreSQL и MySQL/MariaDB. SQLite является готовым к развёртыванию вариантом по умолчанию. Runtime читает `config/database.json`, инициализирует выбранную базу после дешёвой регистрации runtime/модулей, но до загрузки мира, и останавливает запуск, если обязательное хранилище недоступно или не может создать единую baseline-схему Vega 1.0.

## Конфигурация

Настройки по умолчанию:

```json
{
  "provider": "sqlite",
  "sqlitePath": "data/vega.db",
  "busyTimeoutMilliseconds": 5000,
  "connectionStringEnvironmentVariable": "VEGA_DATABASE_CONNECTION_STRING",
  "connectionString": null
}
```

Допустимые значения `provider`: `sqlite`, `postgresql` (`postgres`) и `mysql` (`mariadb`). Относительный путь SQLite вычисляется от каталога распакованного сервера.

Для PostgreSQL:

```powershell
$env:VEGA_DATABASE_CONNECTION_STRING = 'Host=db.example;Database=vega;Username=vega;Password=...;SSL Mode=VerifyFull'
```

Для MySQL/MariaDB:

```powershell
$env:VEGA_DATABASE_CONNECTION_STRING = 'Server=db.example;Database=vega;User ID=vega;Password=...;SslMode=VerifyFull'
```

После этого достаточно изменить `provider` в `config/database.json`. Переменная окружения имеет приоритет над `connectionString`, поэтому пароль не требуется хранить в архиве. Если выбран внешний провайдер без строки подключения, Vega завершает запуск с понятной ошибкой и не переключается молча на SQLite.

## Схема и поведение

Сейчас `vega_schema_history` содержит одну запись `vega-1.0-baseline`. Публичной схемы Vega ещё не было, поэтому прежняя development-последовательность схлопнута и не считается контрактом совместимости. SQLite и PostgreSQL создают полную baseline-схему транзакционно. DDL в MySQL выполняет неявный commit, поэтому Vega удерживает именованную блокировку на уровне выбранной базы и применяет идемпотентный baseline DDL до записи этой единственной версии. Нумерованные forward-only миграции появятся только после публикации первой схемы.

Первая схема реализует постоянную реплику глобальных банов. Создание и отзыв используют монотонные ревизии: устаревшая или повторная доставка не перезаписывает новое состояние. Отзыв сохраняется как tombstone, даже если он пришёл раньше старого события создания. Истёкшие и отозванные баны не попадают в активный snapshot.

Это инфраструктура, а не универсальный DAL. `Vega.Contracts` публикует доменные репозитории и не отдаёт SQL или `DbConnection` в Core и `ServerPlugins`.

## Резервное копирование и восстановление

Перед обновлением Vega через выпущенную версию схемы создайте резервную копию:

- SQLite: остановите Vega и скопируйте `data/vega.db` вместе с файлами `-wal`/`-shm` либо используйте online backup SQLite;
- PostgreSQL: используйте `pg_dump` согласно принятой политике учётных данных и хранения копий;
- MySQL/MariaDB: используйте `mysqldump` либо согласованный snapshot платформы.

Vega отказывается открывать схему новее поддерживаемой текущим бинарным файлом. Запустите соответствующую версию Vega либо восстановите копию до обновления; не редактируйте `vega_schema_history` вручную для принудительного downgrade.

SQLite, MySQL и PostgreSQL проходят единый контракт хранения и резервного копирования. В CI также проверяются все шесть комбинаций источника TShock SQLite/MySQL и назначения Vega SQLite/MySQL/PostgreSQL на отдельных тестовых базах. Внешние тесты используют MySQL 8.4 и PostgreSQL 17. Смена `provider` выбирает другое хранилище, но не переносит автоматически существующую базу Vega. SSC, вайтлист и варпы используют штатные общие или привязанные к миру файловые хранилища независимо от выбранной СУБД.
